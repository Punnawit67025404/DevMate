1. "จากแนวคิด 'Software Entropy' และ 'Broken Window Theory' ลองมองย้อนกลับไปในโปรเจกต์ที่คุณเคยทำ มี 'หน้าต่างที่แตก' บานไหนที่คุณเคยปล่อยปละละเลย และมันส่งผลกระทบอย่างไรในระยะยาว?"

หน้าต่างที่แตกในอดีต: การเขียนโค้ดรีบๆ ให้เสร็จ (Spaghetti Code) ตั้งชื่อตัวแปรมั่ว และไม่เขียนเอกสารกำกับ (No Documentation)

ผลกระทบระยะยาว: เกิด Software Entropy โค้ดเสื่อมโทรมอย่างรวดเร็ว เมื่อเวลาผ่านไปแค่ 2 สัปดาห์ สมาชิกในทีมคนอื่นไม่เข้าใจโค้ดและไล่หาบั๊กยากมาก สุดท้ายทุกคนในทีมเริ่มปล่อยปละละเลยตาม เพราะเห็นว่ามีจุดที่เละอยู่แล้ว ส่งผลให้โปรเจกต์ล่าช้าและระบบพังในที่สุด

2. "อธิบายหลักการ 'Take Responsibility' ในความเข้าใจของคุณ และยกตัวอย่างสถานการณ์ที่คุณจะนำหลักการ 'Provide Options, Don't Make Lame Excuses' ไปใช้ในการสื่อสารกับเพื่อนร่วมทีมในโปรเจกต์นี้"

Take Responsibility ในความเข้าใจของผม: คือการเป็นเจ้าของงาน (Ownership) 100% รับผิดชอบต่อผลลัพธ์และเดดไลน์ของตั๋วงานที่ตัวเองรับมา หากเกิดข้อผิดพลาดจะไม่โบ้ยให้ปัจจัยภายนอก แต่จะยอมรับและมุ่งหาทางแก้ไขทันที

ตัวอย่างสถานการณ์ในโปรเจกต์นี้:
สมมติผมทำระบบจับคู่สกิล (Matching) ไม่ทันตามเดดไลน์เพราะติดปัญหาเทคนิคบน Supabase

สิ่งที่ไม่ควรทำ: "โทษทีนะ Supabase เขียนยากมาก แถมช่วงนี้ติดสอบด้วย เลยทำไม่เสร็จ"

สิ่งที่ควรทำ: "ทุกคนครับ ระบบจับคู่ติดปัญหา Query บน Supabase คาดว่าส่งคืนนี้ไม่ทัน แต่ผมเตรียมทางเลือกไว้ 2 ทางคือ (1) เปลี่ยนมาเขียนฟิลเตอร์แบบง่ายฝั่ง Client-side เพื่อให้ส่งงานผ่านไปก่อน หรือ (2) ขอแรงเพื่อนที่งานเสร็จแล้วมาช่วยคอลรีวิวไล่โค้ดตรงนี้ด้วยกันสัก 20 นาที ทีมเห็นว่ายังไงดีครับ?"
